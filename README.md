# FoodVision

Пилотный сквозной сценарий: загрузка видео со статичной камеры, настройка столов и зон посадки, оценка состояния столов и просмотр результата вместе с исходной записью.

## Запуск на Windows с Docker Desktop и NVIDIA GPU

1. Установите Docker Desktop с поддержкой NVIDIA GPU и свежий драйвер NVIDIA.
2. Поместите подготовленную pose-модель `models/yolo11x-pose.onnx` в `models/`.
3. Скачайте модели обнаружения объектов и людей: `powershell -ExecutionPolicy Bypass -File scripts/setup-models.ps1` (источники — [YOLO11-ONNX](https://huggingface.co/unileon-robotics/YOLO11-ONNX) и [YOLO26l ONNX](https://huggingface.co/qtpose/yolo26l-detect-onnx)). Скрипт проверяет SHA-256 YOLO26l. Веса YOLO26l распространяются под AGPL-3.0; для коммерческого применения проверьте условия лицензирования.
4. Запустите `docker compose up --build`.
5. Откройте <http://localhost:8081>, выберите видео и нажмите «Найти столы».

API и health-check доступны на `http://localhost:8080` и `/health`. Модели монтируются в контейнер только для чтения. Инференс выполняется на CUDA GPU; автоматического перехода на CPU нет.

## Проверка backend

Из корня репозитория выполните `dotnet build backend/FoodVision.slnx -c Release` и `dotnet run --project backend/tests/FoodVision.Checks/FoodVision.Checks.csproj -c Release`. Второй запуск проверяет регрессионные сценарии столов и временной шкалы, а также границы модулей: модуль не может ссылаться на инфраструктуру другого модуля, а `Shared` не содержит кода модулей. PostgreSQL подключается только при заданной строке `ConnectionStrings__FoodVision`, поэтому обычный запуск анализа не требует БД.

## Подготовка разметки

Сначала система ищет столы на кадрах видео до первого кадра, где сработал детектор. Она предлагает рамки столов и предварительные зоны посадки. Перед анализом пользователь может перемещать границы, добавлять и удалять столы, а также менять, добавлять и удалять зоны посадки. Если столы не найдены, их можно добавить вручную. В анализ передаётся только подтверждённая разметка.

Координаты заданы долями ширины и высоты кадра от 0 до 1. Зона посадки обозначает область, где ожидается сидящий гость. Прохожий или стоящий рядом человек сам по себе не получает состояние «гости за столом»; сомнительная поза может привести к состоянию «нужна проверка».

## Анализ и ограничения

FFmpeg декодирует видео с частотой, заданной `Analysis:SamplingFramesPerSecond` (по умолчанию один кадр в секунду). YOLO обнаруживает людей и оценивает посадку по позе. Видимый сидящий человек, чьи бёдра попадают в зону посадки, даёт состояние «гости за столом». Детектор COCO также ищет рюкзаки, сумки и чемоданы на области стола или посадки; это эвристическое состояние «гостей нет, стол занят вещами». Отсутствие этих обнаружений означает только «гостей и вещей нет», а не готовность стола к следующей посадке. Закрытый обзор или признаки недостаточной уверенности дают «нужна проверка».

Автоматическая разметка зависит от обзора камеры, освещения, масштаба и COCO-детектора, поэтому может пропускать столы или ошибаться в их границах. Pose-модель и прямоугольные зоны не всегда различают сидящего гостя и человека в необычной позе. Обнаружение вещей ограничено классами COCO (рюкзак, сумка, чемодан), может пропускать другие предметы и принимать постоянные предметы интерьера за оставленные. Пользователь должен проверить предложенные рамки и зоны. Распознавание на конкретной камере нужно отдельно оценивать; работоспособность приложения не подтверждает точность модели.

Результат содержит исходное видео, рамки столов и шкалу состояний. Нажатие на интервал шкалы перемещает воспроизведение к его началу.

## Нагрузочный бенчмарк на 20 потоков

Режим «Бенчмарк» доступен в веб-приложении отдельно от анализа загруженного видео. Положите `Sample_Video_1.mp4` в `videos/`, обе ONNX-модели — в `models/`, затем запустите `docker compose up --build` и откройте <http://localhost:8081>. Подключитесь к backend, нажмите «Запустить бенчмарк» и остановите прогон кнопкой или дождитесь конца ролика. Необходимы Docker Compose с NVIDIA GPU, драйвер NVIDIA и FFmpeg (уже установлен в backend-образе).

Backend запускает по отдельному FFmpeg-декодеру для каждого потока. Видео передаётся через WebSocket бинарными кадрами RGBA 640×360 с частотой 5 кадр/с. Каждый пятый кадр отдельно проходит object detection, обнаружение людей YOLO26l и pose detection; целевая частота аналитики задаётся `Analysis:SamplingFramesPerSecond` (по умолчанию 1 кадр/с). Результат pose-модели сопоставляется с рамками YOLO26l для оценки посадки; люди без уверенно сопоставленной позы сохраняются с неопределённой позой. Начальные кадры каждого потока используются для независимого предложения расположения столов и зон, затем кадры проходят существующие назначение людей столам и классификацию состояний. Инференс бенчмарка выполняется с ограниченным параллелизмом `Analysis:BenchmarkGpuConcurrency` (по умолчанию 2, диапазон 1–10; в Docker Compose задано 10); обычный анализ получает GPU эксклюзивно. 20 потоков независимы по декодированию и состоянию анализа. Счётчики обработанных кадров показывают фактическую работу модели для каждого потока.

Видео декодируется независимо от инференса; для аналитики каждый поток хранит один ожидающий кадр. При перегрузке новый кадр заменяет ожидающий, а счётчик «заменено при перегрузке» показывает потери. Счётчик «не выбрано аналитикой» показывает намеренную выборку с 5 кадров/с до целевой частоты аналитики; «вне временного бюджета» отдельно считает результаты, готовые позже запланированного интервала. На страницу одновременно передаётся видео десяти выбранных потоков, остальные продолжают декодирование и аналитику. Доставка видео может замедлиться из-за медленного WebSocket-клиента; инференс всех потоков делит одну GPU-очередь и может не достигать целевой частоты.

Перед запуском потоков модели прогреваются на отдельном кадре. Прогрев не входит в счётчики и длительность бенчмарка; во время него на странице показана подготовка. После старта результаты по-прежнему могут отставать от видео при перегрузке GPU.

Карточка потока показывает частоту доставки и инференса, число принятых/обработанных кадров и кадры, обработка которых заняла больше бюджета одного аналитического интервала. Задержка рассчитана от запланированного времени кадра относительно начала прогона до окончания инференса; указаны среднее, p95 и максимум. Клиентская задержка измеряется от отправки кадра сервером до его отрисовки в canvas браузера и также показывает среднее, p95 и максимум; расчёт использует часы сервера и браузера, которые должны быть синхронизированы. Счётчики детекций относятся к последнему обработанному кадру. CPU и RAM — использование процесса backend. Загрузка GPU и VRAM отмечены как недоступные, поскольку сборщик NVIDIA telemetry не включён. Длительность и исходная частота ролика доступны в локальном файле через ffprobe; перед публикацией результатов зафиксируйте модель, GPU, версию приложения и параметры запуска. Прогон не является оценкой точности распознавания.

Остановка посылает отмену всем декодерам; закрытие WebSocket также завершает процессы FFmpeg. Если файл или модель отсутствует, интерфейс показывает ошибку. Для сохранения результата используйте копирование отображённых счётчиков или снимок экрана: постоянное серверное хранение отчёта не включено.

Полный локальный прогон на 10 потоках и измеренные результаты записаны в [отчёте бенчмарка](docs/validation/benchmark-10-streams.md).
