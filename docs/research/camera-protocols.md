# Протоколы для IP-камер и сервиса видеоаналитики

Дата проверки: 2026-11-16. Оценки задержки и эффективности ниже являются качественными: итог зависит от кодека, GOP, битрейта, сети, реализации камеры и сервера.

## Разделение обязанностей

ONVIF не заменяет транспорт видеопотока. Это профиль совместимости и Web Services-интерфейсы для обнаружения и настройки камеры, получения URI потока, PTZ, событий и метаданных. Сам поток обычно забирают по RTSP/RTP. Для покупки камеры нужно требовать подтверждённую совместимость с конкретным ONVIF-профилем и проверять её в базе ONVIF, а не полагаться на надпись «ONVIF».

- **Profile S**: базовый поток, конфигурация, PTZ, аудио, multicast и relay outputs. Подходит как минимум для старых/простых камер.
- **Profile T**: современный видео-профиль: H.264/H.265, imaging, события движения/саботажа, metadata и двустороннее аудио. Включает HTTPS streaming как опциональную возможность профиля; это не означает, что каждая конкретная камера поддерживает TLS/SRTP.
- **Profile M**: метаданные и события аналитики: object counter, классификация, лица/тело, номерные знаки, геолокация. Полезен, если часть аналитики делает сама камера; не заменяет собственную модель CV.

## Таблица протоколов

| Протокол / роль | Задержка | Эффективность транспорта | Защита «из коробки» | Практическое место |
|---|---|---|---|---|
| **ONVIF (S/T/M)** — discovery, настройка, события | Не переносит видеокадры | Не применимо | Зависит от HTTPS/TLS и учётных данных устройства | Основной слой интеграции и инвентаризации камер; URI потока брать через ONVIF |
| **RTSP + RTP/RTCP** — камера → edge-сервис | Низкая | Высокая: поток без сегментации; RTP для медиа, RTCP для статистики/обратной связи | Низкая без дополнительной защиты: RTP/RTCP сами не дают конфиденциальности/аутентичности | Рекомендуемый основной ingest в локальной сети; обычно наиболее совместим с IP-камерами |
| **RTSPS / защищённое туннелирование RTSP и медиа** | Низкая–средняя | Хорошая, но TCP может повышать задержку при потерях | TLS защищает управление; видео защищено только при передаче внутри защищённого канала либо с SRTP | Проверять отдельно защиту управления и медиапотока, поддержку камерой, клиентом и сертификаты |
| **SRTP/SRTCP** — защищённый RTP | Низкая | Почти как RTP, с криптографическими накладными расходами | Высокая: конфиденциальность, аутентификация и защита от повторов | Хороший вариант, но совместимость IP-камер нужно проверять отдельно; ONVIF Profile T сам по себе не гарантирует SRTP |
| **SRT** — contribution между edge и ЦОД | Низкая, настраиваемая | Высокая для нестабильных WAN: UDP, восстановление потерь и контроль задержки | Опциональное AES-шифрование; нужны корректная настройка секрета и контроль доступа | Полезен для передачи уже принятого потока от точки общепита в ЦОД через интернет; поддержку камерой нужно проверять |
| **WebRTC** — сервер → браузер оператора | Очень низкая | Хорошая для одного/небольшого числа зрителей; fan-out требует media server/SFU | Высокая: WebRTC использует DTLS-SRTP; всё равно нужны защищённые signalling/TURN и контроль доступа | Лучший выбор для интерактивного live-просмотра тревоги в веб-интерфейсе, не для прямого массового ingest камер |
| **HLS / LL-HLS** — сервер → много браузеров | HLS: выше; LL-HLS: низкая для HTTP-вещания | Очень высокая масштабируемость через обычные HTTP-серверы/CDN; сегментация добавляет задержку и упаковку | Хорошая при HTTPS и авторизации URL/приложения | Наблюдение и воспроизведение для множества пользователей. LL-HLS снижает задержку, но не заменяет WebRTC для интерактива |
| **RTMP / RTMPS** — encoder → media server | Низкая–средняя | TCP упрощает ingest, но head-of-line blocking ухудшает работу при потерях | RTMP: нет; RTMPS: TLS | Только совместимость с существующими энкодерами/стриминговыми платформами. Не выбирать для новых IP-камерных интеграций и browser playback |

## Что означает «безопасно»

RTSPS сам по себе не доказывает шифрование отдельного RTP/UDP-потока. Для полной защиты нужны SRTP, передача медиа внутри защищённого туннеля либо VPN. RTSP 2.0 не следует считать универсально поддерживаемым камерами: на практике требуется проверка конкретной версии и реализации RTSP, включая распространённый RTSP 1.0.

Шифрование протокола не защищает систему без сетевой и операционной настройки. Камеры должны находиться в отдельном VLAN/подсети без прямого доступа из интернета; сервис получает доступ к ним по allowlist. Нужны уникальные пароли/сертификаты, отключение лишних сервисов и UPnP, регулярные обновления firmware, журналирование доступа и короткоживущие токены к просмотру. TLS защищает соединение, SRTP — медиа RTP и RTCP, SRT с AES — SRT-трафик; RTSP/RTP без этих механизмов передаёт управление/медиа без криптографической защиты.

## Рекомендованный маршрут для точки общепита

1. Edge-agent в локальной сети находит и настраивает камеры через **ONVIF Profile T** (fallback Profile S), получает RTSP URI и читает события.
2. Agent принимает основной RTSP-поток для архива и лёгкий substream для аналитики; декодирует кадры аппаратно, отправляет выбранные кадры в inference, а в ЦОД передаёт только события, метаданные и нужные клипы.
3. Если из точки в ЦОД идёт живое видео через ненадёжный WAN, gateway передаёт его по **SRT с AES** либо по TLS-защищённому каналу. Камеры не публикуются наружу.
4. Медиа-сервер в ЦОД раздаёт **WebRTC** для живой тревоги оператора и **HLS/LL-HLS** для обычного просмотра. Не следует создавать отдельное RTSP-подключение к камере на каждого зрителя.

## Первичные источники

- [ONVIF Profiles](https://www.onvif.org/profiles/) — назначение профилей и оговорка, что соответствие регулированию вне области ONVIF.
- [ONVIF Profile S](https://www.onvif.org/profiles/profile-s/) — поток и базовые функции видеосистемы.
- [ONVIF Profile T](https://www.onvif.org/profiles/profile-t/) и [Profile T specification](https://www.onvif.org/wp-content/uploads/2018/09/ONVIF_Profile_T_Specification_v1-0.pdf) — современное видео и варианты RTP/RTSP/HTTPS/TCP.
- [ONVIF Profile M](https://www.onvif.org/profiles/profile-m/) — метаданные, события и аналитические классы объектов.
- [ONVIF Core Specification](https://www.onvif.org/specs/core/ONVIF-Core-Specification.pdf) — ONVIF management/control interfaces как Web Services.
- [RFC 7826 (RTSP 2.0)](https://www.rfc-editor.org/info/rfc7826/) — RTSP как протокол установки и управления real-time delivery.
- [RFC 3550 (RTP/RTCP)](https://www.rfc-editor.org/info/rfc3550/) — RTP не гарантирует QoS; RTCP мониторит доставку и даёт минимальную обратную связь.
- [RFC 3711 (SRTP)](https://www.rfc-editor.org/info/rfc3711/) — конфиденциальность, аутентификация и replay protection для RTP/RTCP.
- [RFC 8827 (WebRTC Security Architecture)](https://datatracker.ietf.org/doc/html/rfc8827) — модель безопасности WebRTC.
- [WebRTC: TURN server](https://webrtc.org/getting-started/turn-server) — при NAT часто нужен relay/TURN.
- [Apple: HTTP Live Streaming](https://developer.apple.com/streaming/) и [Enabling Low-Latency HLS](https://developer.apple.com/documentation/http-live-streaming/enabling-low-latency-http-live-streaming-hls) — HTTP/CDN-масштабирование и компромисс HLS между надёжностью и задержкой.
- [Haivision SRT documentation 1.5.4](https://doc.haivision.com/SRT/1.5.4/Haivision/introduction-to-srt) — SRT, UDP-происхождение и AES encryption; в production следует сверить версию реализации.
- [Adobe RTMP Specification 1.0](https://ossrs.io/lts/en-us/assets/files/rtmp_specification_1.0-25a467618b92a3115bc97d4b0038b0ff.pdf) — историческая спецификация RTMP; отдельная стандартизация IETF отсутствует.
