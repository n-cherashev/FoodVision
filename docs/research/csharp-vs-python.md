# C# и Python для полноценного сервиса видеоаналитики

Дата исследования: 2026-11-16. Это сравнение архитектур и инженерных затрат, не измерение производительности. Предполагаются одинаковые камеры, оборудование, модель и требования к продукту.

## Основной вывод

Оба языка подходят для полноценного продукта. При постоянных экспериментах, дообучении и разработке новых CV-сценариев Python уменьшает объём интеграционной работы. При готовой совместимой модели и .NET-команде C# подходит для всего работающего сервиса. Обучение в Python не требует Python в production: результат обучения может поставляться как ONNX-артефакт.

Следует различать две трактовки «всё на C#»: весь production без Python и весь жизненный цикл, включая обучение, без Python. Первый вариант практичен для совместимых моделей; второй возможен, но ограничивает доступ к готовым исследовательским пайплайнам.

## Сравнение

| Область | C# | Python |
|---|---|---|
| Готовая ONNX-модель | Официальный ONNX Runtime API; проверить входы, выходы и postprocessing | Официальный runtime; часто есть также исходный SDK модели |
| Готовая модель только с Python SDK | Нужны поддержанный экспорт, портирование либо внешний процесс | Прямое использование при совместимых зависимостях |
| Дообучение | Возможно через TorchSharp, но конкретные архитектуру, загрузку весов и data pipeline нужно проверить | Обычно можно использовать исходный training pipeline автора |
| Новая архитектура | Больше вероятного портирования исследовательского кода | Проще использовать новые модели и воспроизводить исследования |
| API и бизнес-логика | Статическая типизация и единая экосистема .NET удобны для команды с соответствующим опытом | Полноценный backend возможен; полезны аннотации, статическая проверка и runtime-валидация границ |
| CPU-код вокруг модели | Компилируемый код и средства управления буферами удобны | Избегать Python-циклов по пикселям; использовать native/vectorized операции |
| GPU inference | Зависит от backend, модели, подготовки данных и копирований | Те же факторы; интерпретатор не выполняет CUDA-ядра модели |
| Развёртывание | .NET плюс native runtime/декодер/драйверы | Python плюс native runtime/декодер/драйверы; версия Python и пакеты также важны |
| Надёжность | Нужны ограниченные очереди, контроль ресурсов, watchdog и recovery | Нужны те же механизмы; язык сам их не обеспечивает |

## Готовая модель

Для очередей можно начать с детектора людей, но очередь определяется зоной, временем и правилами. Универсальный детектор не обязан содержать классы перчаток или головных уборов; смена имени класса не создаёт новый навык распознавания. Для специальных классов нужны подходящие веса или дообучение.

C# маршрут: FFmpeg/GStreamer -> кадры -> подготовка входного тензора -> ONNX Runtime -> обработка выходов -> tracker -> правила -> событие. OpenCvSharp может использоваться для операций над изображением; это wrapper с native-зависимостями, а не замена всем функциям видеосервера.

Python маршрут: FFmpeg/GStreamer -> подготовка кадров -> SDK модели либо ONNX Runtime -> tracker -> правила -> событие. Исходный SDK может уже включать resize/letterbox, нормализацию, декодирование результатов и NMS. При сравнении нельзя принимать отсутствие этого кода в примере Python за отсутствие вычислений.

NMS нужен не всем архитектурам; обработку результатов следует определять по контракту конкретной модели. Расширение .pt не гарантирует загрузку произвольной Python-модели в C#.

Первичные источники: [ONNX Runtime C# tutorial](https://onnxruntime.ai/docs/tutorials/csharp/basic_csharp.html), [Ultralytics export](https://docs.ultralytics.com/modes/export), [OpenCvSharp](https://github.com/shimat/opencvsharp).

## Обучение и поставка

Практический цикл: собрать реальные независимые видео -> разметить -> разделить train/validation/test по дням/площадкам/роликам -> проверить baseline -> дообучить -> оценить события -> экспортировать -> проверить parity -> выпустить модель с возможностью отката.

Для поставки сохранять не только веса, но также версию модели, классы, входной размер, преобразование цвета, нормализацию, letterbox/resize, формат выходов и совместимые версии runtime. Порог уверенности и правила событий тоже версионировать. Обучение выполнять отдельной задачей с отдельным бюджетом CPU/GPU; не конкурировать им с рабочей аналитикой без явного управления ресурсами.

TorchSharp предоставляет доступ к LibTorch и позволяет обучать модели на .NET, но наличие библиотеки не обеспечивает прямую совместимость с любым готовым Python-проектом. Оценку удобства делать для выбранной архитектуры, а не для тензорных операций вообще.

Первичные источники: [TorchSharp](https://github.com/dotnet/TorchSharp), [TorchSharp examples](https://github.com/dotnet/TorchSharpExamples), [PyTorch fine-tuning](https://docs.pytorch.org/tutorials/intermediate/torchvision_tutorial.html), [PyTorch ONNX exporter and verification](https://docs.pytorch.org/docs/stable/onnx.html), [ORT compatibility](https://onnxruntime.ai/docs/reference/compatibility).

## Производительность и эксплуатация

Полная задержка: получение кадра + декодирование + preprocessing + очереди/batching + GPU transfers + inference + postprocessing + rules. Показатель inference FPS нельзя подменять end-to-end FPS и задержкой тревоги. При одном runtime преимущество языка по inference заранее не доказано.

Обычный CPython с GIL ограничивает параллельное исполнение Python bytecode в потоках; native-библиотеки могут освобождать GIL и использовать собственные потоки. Free-threaded сборки существуют, но требуют проверки совместимости расширений. Async не ускоряет CPU/GPU вычисления автоматически.

Не создавать копию GPU-модели на каждый API-worker или каждую камеру без расчёта памяти. Выделить video-worker и API в разные процессы при необходимости изоляции, даже если оба написаны на одном языке. В .NET native crash также может завершить процесс; управляемый язык не отменяет этот риск.

Источники: [Python free threading](https://docs.python.org/3/howto/free-threading-python.html), [ORT I/O Binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html), [ORT threads](https://onnxruntime.ai/docs/performance/tune-performance/threading.html), [FastAPI deployment and worker memory](https://fastapi.tiangolo.com/deployment/concepts/), [.NET Worker Services](https://learn.microsoft.com/en-us/dotnet/core/extensions/workers).

## Как выбрать для FoodVision

- Готовые модели, стабильные сценарии, сильная .NET-команда: production C# + ONNX Runtime.
- Частые эксперименты, специализированные классы, сложные действия: Python для всего сервиса — разумный исходный выбор.
- Production C# с периодическим Python-обучением: самостоятельный вариант без обязательного постоянного Python-сервиса.
- Строго один язык для продукта и обучения: Python предпочтительнее по доступности готовых training pipelines; C# выбирать после доказательства реализуемости нужного обучения через TorchSharp.

Для выбора производительности сравнить один и тот же ONNX-артефакт и одинаковый preprocessing на целевом оборудовании. Измерить p95 задержки, пропуски кадров, CPU/RAM/VRAM, ложные тревоги, время восстановления потока. Второй отдельный эксперимент — время интеграции новой модели на каждом языке. Бенчмарки и точные сроки в рамках исследования не выполнялись.
