# Видеомониторинг общепита: архитектура и CV

Дата проверки источников: 2026-11-16. Это исследование вариантов, а не результаты испытаний оборудования. В репозитории на момент исследования нет исходного приложения. Выбор ниже — инженерная рекомендация при неизвестных числе камер, моделях камер и целевых событиях.

## Рекомендуемая схема

IP-камеры -> локальный узел захвата и анализа -> HTTPS -> центральный API, события, клипы и веб-интерфейс.

Локальный узел инициирует соединения к камерам в LAN. Он может подключаться непосредственно к камерам или к NVR, если тот предоставляет нужные потоки. Для аналоговых камер нужен регистратор/энкодер. Для камер с закрытым облачным доступом необходимо отдельно проверить наличие локальных потоков/API.

ONVIF используется для совместимого обнаружения, конфигурации и получения URI; видео обычно получают через RTSP/RTP. ONVIF не обязателен при заранее известном RTSP URI. Поддержка функций зависит от профиля, прошивки и конкретного устройства. Подробности и первичные источники: [протоколы](camera-protocols.md).

Локальная обработка уменьшает постоянный исходящий видеотрафик и может продолжаться без интернета. Для этого необходимы локальные очередь событий и буфер клипов с повторной отправкой после восстановления связи. Цена — оборудование и сопровождение узла на каждой площадке. Централизованный анализ также допустим при подходящих каналах и экономике.

Предлагаемые меры: отдельный сегмент камер, уникальные учетные записи с минимальными правами, отсутствие публикации портов камер в интернет, TLS/VPN для WAN, безопасное хранение секретов, разграничение доступа к клипам и политика удаления. Это рекомендации по устройству системы, не юридическое заключение.

## Видеотракт

Получение сжатого потока -> декодирование -> выбор кадров -> resize/нормализация -> inference -> tracking -> временные правила -> событие и клип.

FFmpeg поддерживает RTSP и варианты нижележащего транспорта, включая UDP и TCP interleaving: [официальная документация](https://ffmpeg.org/ffmpeg-protocols.html#rtsp).

Рекомендуется выделить захват, inference и отправку событий в независимые этапы, ограничить очереди, использовать временные метки кадров, отслеживать зависший поток и переподключаться с задержкой. Для live-анализа обычно лучше отбрасывать устаревшие кадры, чем накапливать задержку; для полноты архива нужен отдельный тракт записи. Сжатый архив при совместимых контейнере и кодеке можно сохранять без перекодирования; границы клипов зависят от ключевых кадров.

Выбор main/substream зависит от задачи: для очереди допустимо уменьшать разрешение; для мелких предметов и перчаток это может уничтожить нужные детали. Снижение частоты inference не гарантирует пропорционального снижения затрат на декодирование межкадрового видео.

Иллюстративная арифметика, не замер: 8 камер по 4 Мбит/с = 32 Мбит/с и примерно 345,6 ГБ/сутки непрерывного видео, без накладных расходов. 8 камер по 5 анализируемых кадров/с = 40 кадров/с inference. Ни одно число не определяет подходящую GPU без измерений полного тракта.

## Python и C#

Python рекомендуется для исследования, подготовки данных, обучения и первых CV-пайплайнов. PyTorch/Torchvision показывает дообучение детектора на собственном датасете: [официальный tutorial](https://docs.pytorch.org/tutorials/intermediate/torchvision_tutorial.html).

C# подходит для центрального API, конфигурации камер, авторизации, событий и запуска совместимых готовых моделей. ONNX Runtime имеет официальный C# API и аппаратные execution providers: [C#](https://onnxruntime.ai/docs/get-started/with-csharp.html), [providers](https://onnxruntime.ai/docs/execution-providers/), [CUDA и совместимость](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html).

Рекомендация для .NET-команды: ASP.NET Core для продукта и Python для экспериментов/CV-worker; после стабилизации модели оценить C# + ONNX Runtime. Python-worker обрабатывает видео рядом с источником и отправляет компактные события; не стоит пересылать каждый raw-кадр через JSON/HTTP. Гибрид добавляет сопровождение двух сред, поэтому полностью Python MVP также разумен.

ONNX не гарантирует перенос любой модели: проверить экспорт, операции, dynamic shapes, pre/postprocessing, поддерживаемую точность и совпадение результатов с исходной моделью. Native runtime под Python и C# может выполнять одинаковые вычисления; скорость определяют также копирования памяти, декодер, preprocessing, модель и batching. Сам язык не доказывает преимущество по FPS.

## Стек-кандидат

- Захват: FFmpeg либо GStreamer, с проверенным аппаратным декодером при необходимости.
- Данные и обучение: Python, PyTorch, CVAT для разметки. CVAT поддерживает средства работы с детекциями и треками: [документация](https://docs.cvat.ai/docs/annotation/tools/ai-tools/).
- Детектор: сравнить модели семейства YOLO и другие детекторы на видео площадки, а не выбирать по названию. Пример с ONNX/TensorRT deployment: [YOLOX](https://github.com/Megvii-BaseDetection/YOLOX).
- Tracking: [ByteTrack, первичный репозиторий](https://github.com/FoundationVision/ByteTrack). Track ID — техническая идентичность в последовательности, не установленная личность человека; трек может обрываться или менять ID.
- Inference: ONNX Runtime как начальная переносимая база; TensorRT/DeepStream как кандидат для NVIDIA; OpenVINO как кандидат для Intel, после проверки поддержки конкретного железа и модели.
- Продукт: ASP.NET Core либо Python API, PostgreSQL для конфигурации/событий, локальный диск или объектное хранилище для клипов, контейнерное развертывание. Это варианты дизайна, не обязательный набор зависимостей.

DeepStream строит GStreamer pipeline с аппаратными декодированием, preprocessing, batching, inference, tracking и отправкой metadata. Текущая документация рекомендует pyservicemaker вместо deprecated старых Python bindings: [DeepStream overview](https://docs.nvidia.com/deepstream/text/DS_Overview), [Python Pipeline API](https://docs.nvidia.com/deepstream/text/DS_service_maker_python_intro_to_pipeline_api). Выбор DeepStream привязывает обработку к экосистеме NVIDIA.

Лицензии кода, весов и обучающих данных необходимо проверять отдельно. Ultralytics публикует варианты AGPL-3.0 и Enterprise; это существенное условие выбора для закрытого продукта: [условия производителя](https://www.ultralytics.com/license). Экспорт ONNX сам по себе не снимает исходные лицензионные условия.

## Что действительно распознается

Детектор оценивает классы объектов и их координаты на кадре. Tracker связывает наблюдения между кадрами. Правила используют геометрию зон, длительность, последовательность событий и пороги для создания продуктового события.

Очередь: люди в полигоне зоны ожидания, отделение обслуживаемых людей и персонала, временной порог, подавление повторов. Шапочки и перчатки: специализированные классы, достаточное число пикселей на объект и проверка видимости. Мытье рук и соблюдение рецептуры: нужна последовательность действий, часто несколько ракурсов и внешние данные. Видеокамера наблюдает видимое действие; она не измеряет микробиологическую чистоту или внутреннюю температуру еды. Для температуры нужны соответствующие датчики.

Обучение обычно начинают с предобученной модели, размечают реальные видео и дообучают при недостаточном качестве. Разделять train/validation/test следует по независимым видео/дням/площадкам: соседние кадры одного фрагмента в разных выборках дают утечку. Измерять precision/recall на событиях, ложные тревоги на камеро-час, задержку, долю потерь и надежность восстановления, а также качество модели на кадрах.

## Предлагаемый первый пилот

Одна площадка, несколько реальных камер, одно измеримое событие — например очередь выше согласованного порога дольше заданного времени. Сначала зафиксировать видимость и эталонные события, затем сравнить модель на независимом видео, добавить live-захват, правила, клипы и восстановление после сбоев. Железо выбирать после замера полного pipeline на целевых потоках. Число камер на GPU заранее не обещать.
